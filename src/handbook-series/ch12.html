Prompt：模板、版本、标签与有效 Prompt

原书 15.1 节

当 Agent、团队和环境变多，Prompt、Skill、MCP、Agent 会从单个应用的局部内容变成被多方依赖的公共资源。原书把承载它们注册、版本、治理、发现和分发的基础设施称为 Agentic Resource Registry，并以开源的 Nacos（3.3 版本线的 AI Registry）作为贯穿全章的参考实现。先看 Prompt：一项可发布的 Prompt 应当是结构化内容，包括指令层（来源明确，低优先级不能覆盖高优先级）、模板与变量（名称、类型、必填、默认值、长度限制）、输入输出要求（输出 Schema）、运行依赖（适用模型、所需工具、知识来源）、验证材料（样例与评测集）。变量替换在受控渲染中完成，用户输入、检索结果、工具返回作为数据进入指定位置，而不是先随意拼接再让模型判断哪些是指令。

变更分三类：文字修订（预期不改目标和结构，仍要评测确认）、接口变化（增加必填变量、改输出 Schema、改工具依赖，直接影响调用方）、行为变化（改判断规则、拒绝范围、结果偏好，输入输出形式不变也可能改变行为）。自然语言的细微调整也可能改变输出，所以很难靠语义化版本号推断兼容性，版本号首先是唯一标识，行为能否接受要靠评测和人工判断；评测记录还要绑定模型版本、推理参数、工具定义和评测集版本，只记一个总分说明不了变化来自哪里。

发布时，确定性要求高的 Agent 固定精确版本；需要集中维护的绑定 stable、canary 等标签，由平台调整指向，历史版本内容永不变，变的只是指向关系。已开始的长任务不宜中途换 Prompt，应在任务或会话开始时解析一次并在该边界内保持不变。模板只是开始，模型实际收到的是有效 Prompt = Prompt 版本 + 变量快照 + 模型与参数 + 工具定义版本 + 策略版本 + Context 来源，运行时为这一组合生成可查询的指纹并写入 Context Manifest，结果偏离时才能分清是 Prompt 变更、模型升级、变量错误还是上下文变化。

Skill：完整能力包与可信准入

原书 15.2 节

Skill 的管理对象是完整能力包，而不只是 SKILL.md：使用说明、manifest.yaml（标识、发现信息、依赖、所需工具、权限范围、资源限制、来源、许可证）、脚本、模板、参考资料、测试和许可。发现效果取决于描述能否准确表达能力边界：“数据分析助手”太宽泛，要说清解决什么任务、需要什么输入、产生什么结果、哪些情况不适用。发布后包内容和依赖锁定信息不能覆盖，摘要要覆盖完整能力包（只对 SKILL.md 算摘要会漏掉脚本和依赖的变化）；兼容性也不只看说明，例如脚本运行时从 Python 3.10 升到 3.12，现有 Agent 就可能用不了。废弃、停止分发、安全撤回是三种不同的处置强度。

外部 Skill 会把外部维护者、代码依赖和内容来源带进运行环境，而 Agent 会按自然语言说明调用文件、命令、工具，一段普通说明也可能间接引导高权限操作。所以要设独立的接收区域，走完六个阶段才形成内部版本：来源核实 → 完整性校验 → 静态检查 → 隔离验证 → 人工评审 → 内部发布。签名和摘要证明“来自谁、检查后没被替换”，不能证明内容本身没风险；静态检查只能识别已知模式。

通过准入的 Skill，运行时也不继承 Agent 的全部能力：按当前任务重新授予必要权限，且不超过 Manifest 声明的范围。只负责整理本地 Markdown 的 Skill，不能因为所在 Agent 有云端管理能力就同时拿到外网和生产系统权限；不需要联网就默认禁网，文件访问限定在任务目录，凭据由运行环境以短期最小权限注入。发布后还要定期重新检查（上游披露漏洞、依赖出问题、行为与声明不一致），确认风险就停止新安装和新解析，并通过反向引用找到受影响的 Agent 与历史任务。

MCP Server 与 Agent Registry：定义与端点分开

原书 15.3–15.4 节

MCP 让 Agent 能连上外部工具，但“能够连接”不等于“能够管理”。核心做法是把相对稳定的能力定义、可以独立发布的版本、持续变化的运行端点分开：一个 MCP Server 版本可以在多个实例和区域运行，扩缩容不产生新版本；Tool 参数、返回结构或说明改变时才形成新版本。删除 Tool、改参数类型、改返回结构会让现有 Agent 失效；新增 Tool 虽不破坏已有调用，却会改变模型看到的候选、影响工具选择；连描述文字的调整也可能让无关任务开始匹配它。所以生产 MCP Server 要同时比较 Schema 差异和代表性任务下的工具选择结果。在线状态、端点健康、版本状态也要分开表达：资源在线不代表每个端点健康，有健康端点也不代表当前调用方有权访问。MCP 协议里的 Prompt 能力跟随 Server 版本，与企业 Prompt Registry 里独立发布的 Prompt 不是一回事。

Agent Registry 管理带版本的 Agent 调用描述（如 A2A 的 AgentCard），同样把逻辑版本与运行端点分开。它和 AgentSpec Registry 是两个层次：前者回答“现在有哪些 Agent 可以被发现和调用”，后者回答“一个 Agent 应如何被描述、组装和分发”（Manifest、Prompt、Skill、MCP 引用、运行配置）。平台可以先按 AgentSpec 构建 Agent，再把 AgentCard 和端点注册到 Agent Registry，但两者不应共用一个版本号。

Nacos 3.3 初步完成了协议无关的远程 Agent 发现 RAD，五个操作把“可能适合”和“当前可以调用”分开：Search 只返回轻量目录（名称、描述、标签、在线版本、支持协议，不含端点）；Discover 解析精确在线版本、协议原生描述和端点快照；Watch 感知快照变化；Register / Deregister 由发布者维护运行地址。“协议无关”不是取消协议，发现完成后，实际消息、任务、流式交互仍由 A2A 等原生客户端完成。

统一发布 Pipeline 与资源中心

原书 15.5–15.6 节

五类资源（Prompt、Skill、MCP Server、Agent、AgentSpec）内容形式不同，但变更都会影响 Agent 行为，所以需要一条公共评审路径：草稿（可修改，运行时查不到）→ 提交评审（固定候选内容和摘要，后续检查都针对同一份内容）→ 检查节点依次执行（格式与引用 → 安全扫描与依赖 → 任务评测，任一拒绝就停）→ 评审通过 → 发布（形成不可变版本）→ 在线与标签决定运行时能否发现。几个原则：检查过程不修改候选内容，需要调整就回到草稿形成新摘要；自动结果不能完全代替人工判断；评测记录绑定资源、版本、摘要、评测集、运行时、策略、检查工具版本，内容或关键条件变了，原评测结果不能沿用；紧急强制发布要记录原因、风险接受人、影响范围和恢复目标，不能成为日常路径。

资源中心的目标是统一标识、生命周期、权限、评审和运行入口，而不是把这些资源改造成同一种内容。Agent 用结构化引用（Namespace、类型、名称、版本选择方式）声明依赖，Resolver 把引用解析为唯一版本和摘要，运行记录保存解析结果而不是标签名。可见范围决定资源是否出现在列表和搜索里，鉴权决定能否读取、修改、发布，两者作用不同；还要维护双向引用关系，才能判断一次撤回影响哪些 Agent。为语义搜索生成的 Document、Chunk、向量是可重建的派生数据，权威在 Registry；旧索引检索到已下线资源，返回前要按 Registry 当前状态再判一次。管理链路（编辑、评审、扫描、建索引）与运行链路（查询、解析、下载、端点发现）在接口和容量上分开，运行侧缓存与精确版本和摘要绑定，查询失败不能被解释为“使用任意可用内容”。

稳态 Agent 与动态 Agent

原书 15.7–15.10 节

稳态 Agent（客服分类、合规审核、固定流程的数据处理）的依赖可以预先声明，资源获取就是“声明引用 → 解析版本 → 校验内容 → 加载或连接 → 记录结果”，重点是确定性而不是搜索。版本确定时机有三种：构建期绑定（内容与 Agent Release 一起固定，离线可用，更新要重新构建）、部署期解析（CI/CD 按环境把 AgentSpec 解析为 Lock Manifest）、启动期拉取（资源可独立更新，依赖资源中心可用性，需要缓存策略）。收到更新不等于立即替换当前任务的内容：先在旁路下载校验，再在下一个清晰的任务边界启用；获取失败时，非关键说明可用已验证缓存并告警，涉及安全策略或法规的 Prompt 可能不允许用过期缓存，应暂停新任务。

动态 Agent（通用运维 Agent 从容器异常转到数据库性能）事先列不全需要的能力，全部预绑定会让配置膨胀、Context 塞满无关说明。ARD（Agentic Resource Discovery）按任务发现：先从任务事实形成结构化的能力需求（不必把敏感原文发给发现服务），再用关键词 + 向量 + 资源关系混合检索。关键一点：相关性决定排序，治理规则决定资格，高度相关但已撤回或超出授权的资源不应出现在可用候选里，过滤要在最终分页前完成，避免总数泄露不可见资源；相关性分数也不是安全评分。生产通常混合：核心 Prompt 和高频基础 Skill 固定，长尾能力按任务发现，高风险的发现结果可以只返回说明、要求人工确认。

发现之后还要进 Context：发现阶段只用摘要比较候选，选定后才按精确版本取执行内容（Skill 先加载主要说明、到特定步骤再读参考；MCP 只呈现授权范围内的必要工具）。优先级不由文本位置决定：发现的 Skill 要求忽略系统策略、Tool 返回里出现类似系统指令的文字，都保持原有的数据或 Skill 层级。能力说明也要与实际授权一致，看得见却无权调用会产生无效规划。一项资源获取失败时，不能随意混合新旧版本（新 Prompt 依赖新输出 Schema，旧 Skill 还缓存着），应整体退回上一组已验证组合或停止任务。原书的端到端案例里，一个已发布的 Skill 后来被发现会把样例数据发到未申报的外部服务：下线版本、ARD 排除、停止新加载、清缓存，再用 Lock Manifest、Context Manifest 和历史 Trace 找到用过它的任务，核查是否真的外发了敏感数据。

两份清单：Agent 要什么，这次实际用了什么

原书 15.7.2、15.9.1–15.9.3、15.9.5 节

上一节讲稳态和动态两种获取能力的方式，落到工程上就是两份清单。AgentSpec 写在发布之前，声明“我要什么”：哪些 Prompt、Skill、MCP Server，按精确版本还是按标签。Context Manifest 在每次调用装配完上下文之后生成，记录“这次实际用了什么”：各资源解析出的精确版本和摘要、策略版本、发现请求、实际连接的端点、内容指纹。前者保证可控，后者保证事后说得清。

两份清单之间是 Context Compiler 的装配。原书强调三点。第一，发现和执行分开：比较候选时只看名字、简介、风险等级这些摘要，选定之后才按精确版本取完整内容，摘要对应的版本如果已经撤回，就拒绝加载、重新发现，不能拿名字相近的东西顶替。第二，优先级看来源，不看位置和措辞（见下表）：发现来的 Skill 要求“忽略系统策略”，或者工具返回里出现像系统指令的文字，都仍然只是 Skill 或数据。第三，按预算渐进装配：先给各类内容分配 token 预算，核心策略和任务指令完整保留，Skill 先给步骤、参考资料延后，MCP 工具只披露当前需要的一小组，后续每次新增内容都要再过一遍版本、权限和预算检查；超出预算时，裁剪要记录保留了什么、省略了什么、为什么。

为什么要 Agent Simulation

原书 16.1–16.2 节

原书第 16 章从一个类比开始：一个医生可能犯错，但医疗系统整体可预期，执业资质卡入口、操作规程约束过程、案例复盘沉淀教训、模拟器训练罕见场景，没有一样在保证“每个医生每次都对”，都在约束一个不可靠的内核。大模型就是那个内核，Harness 在做同样的事。但 Agent 比人少三样制度前提：角色没有外部标准（两个同名“退款 Agent”权限和话术可能完全不同）、失败没有自然代价（没被检测到就没有后果）、身份不连续（同一名字下跑着不同版本，错误随新版本发布被抹平）。这三样以年计，只有模拟不依赖它们，只需要一个可以安全失败的环境。原书的退款例子：人类客服身后有培训考核、SOP、录音抽检、投诉进绩效、年度模拟演练五样保障，换成 Agent 全部归零，第五样是当下就能拿回来的。

Agent Simulation 用软件承载被测 Agent 所处的外部世界，让执行可反复启动、可配置、无真实后果，由用户模拟（会记错金额的顾客、会撤回指令的审批人）和环境模拟（工具与 API、数据与业务状态、文件、模型服务、外部事件和时间）组成。它和 Evaluation、Testing、Governance 是可组合的能力，不是固定流水线。原书纠正了一个流传很广的说法（“只要有一个请求真的发出去就不再是仿真”）：仿真的边界是授权和后果，不是实现方式：不触达未授权的生产账户、数据与网络，不产生不可控的真实副作用，连着隔离的真实数据库也仍是仿真；全是替身但把请求路由到生产账户，那是事故。

执行模式三种：全替身（可复现性最高，适合回归）、混合（部分组件用隔离的真实后端）、隔离真实依赖（真实数据库锁、真实网络栈，适合服务栈验证与故障实验），不同模式的结论不可混用。还有两条硬规矩：被测系统（SUT）不进入仿真，推理、工具选择、参数构造、异常处理一旦被替换，被测对象就移出了回路（把工具调用顺序固定成脚本是最隐蔽的例子，Run 看起来一切正常，测的却是那段脚本）；替换前问一句“这是这次要考察的内容，还是要设定的条件”，内容不能换，条件必须换并写清楚换成了什么。

判断这些设置还算不算仿真；再判断该不该替换。

数据契约与执行引擎

原书 16.3–16.4 节

可复现的前提是对象有明确定义和生命周期：Scenario Spec（场景规格）→ Manifest（启动时锁定的不可变运行配置）→ Run（一次受控执行，含 Task、Session、Event）→ Run Result（Records 原始记录、Artifacts 产物、Observations 事实观测、Evidence 面向评价项的证据引用、Completeness 完整性）。“评价项 → 证据引用 → 判定”由 Evaluation Result 建立，不属于 Run Result：原始材料与质量结论分层，质量团队重评分、合规团队查金额口径、回归系统比版本，才能各自引用同一份材料而不被上一轮结论污染。场景里写的“首次查询时注入超时”是 triggers（计划），命中之后“查询超时已发生”才是 Event，计划和事实不共享名字。Run 的状态沿四个维度独立表达：执行状态、仿真有效性、证据完整性、任务质量，一次完整、有效、材料齐备的 Run 完全可能退错金额，压成一个“成功 / 失败”就说不清是环境坏了还是 Agent 错了。

执行引擎（Simulation Harness）做五件事：解析场景生成 Manifest、编排 Run 生命周期、管理替身与隔离、汇集记录引用、清理环境；不做五件事：任务生命周期管理、鉴权、遥测采集、质量评分、发布决策，每一项都有专职系统，收进来就会膨胀成总控制器。引擎还要记两张账：事件联动账（撤回消息在用户侧产生、被 Agent 收到、对在途事务生效是三个时点）和时间分离账（业务日历时间判断退款期限、仿真逻辑时间调度虚拟事件、单调时钟测真实耗时、墙钟关联现实日期，四者不可混用）。

用户模拟器分三层：Persona（角色底色）、认知状态（她知道什么，允许与客观状态不同，记错金额时真实状态和用户认知两份都留着）、行为策略（被追问三次才给订单号、等两分钟开始威胁投诉）；工程上用状态机选意图、模型生成措辞，再做事实和披露规则校验。模拟器质量不等于 Agent 成功率：过度配合会高估 Agent，始终拒绝会产生无意义失败；生成与评分用不同模型以减少共同偏差。环境模拟器第一要求是事实一致（create_refund 说受理了，get_refund 就必须查得到），超时要按请求生命周期分三个位置注入；故障注入要分四步记录：计划注入、执行器生效、目标命中、恢复验证，“注入了”和“生效了”是两件事。

场景、证据与结论的边界

原书 16.5–16.6 节

场景是对一次受控执行的完整描述：初始条件、参与方、交互规则、允许的演化路径、何时终止。它不是脚本（不固定对话内容），也不是随机生成（有约束和边界），而是允许多条合理路径的声明式规格。资产是场景引用的、独立版本化的材料（用户行为策略、环境数据、工具契约、模拟器配置、评估规格）：改用户耐心参数是新场景版本，改模拟器的披露规则逻辑是新资产版本。用户与环境要联合建模：用户嘴里的订单、工具参数里的订单号、数据库里的记录必须是同一张单子。Scenario Spec 有十个字段组：identity、sut、user、environment、interaction、participants、events、execution、evaluation_ref、provenance。场景材料从四个方向收集（需求与政策、源码与配置、生产会话与 Trace、事故与人工接管记录），生成机制从模板填充、规则派生到 LLM 辅助，工程主流是混合：模板和规则锁结构，LLM 提出变化，校验器筛选。把生产事故的表象直接抄成场景，等于“把未确诊的病历直接开成处方”。

Run Result 交付的是证据材料，不是质量结论：运行完成、任务成功、允许发布是三个互不推导的结论。评估一侧有三道证据检查：记录完整性、运行有效性、证据充分性，证据不足的项目输出“不可判定”，这是诚实的结论。同一份证据包可以服务质量评估、缺陷定位、版本回归与门禁、复现回放、场景提取、模拟器质量治理、性能与成本分析。Testing Gate 汇总证据，但不是发布决定者。

还要读懂统计边界：n 次独立运行零违规，违规率的单侧 95% 置信上界是 1 − 0.051/n，大样本下约 3/n。300 次零违规的意思是“违规率大概率不超过 1%”，而不是零；前提是固定样本量、独立同分布、没有选择性排除。最后，仿真结论建立在会过期的假设上：仿真用户不是真实用户，场景来自已知失败模式，工具契约和用户分布会漂移；仿真成功率上升而生产人工接管持续增加，就是假设过期的信号。校准按事件驱动（接口变更、故障复盘、用户结构变化），而不是固定周期。

先估一下：200 次零违规，违规率上界大约多少？

Simulation 还是 Evaluation 的职责？（原书 16.6 节）

回扣开头的三个问题

先自己答，再点开
1. 有效 Prompt？为什么存精确版本？外部 Skill 为何不能直接用？

有效 Prompt = Prompt 版本 + 变量快照 + 模型与参数 + 工具定义版本 + 策略版本 + Context 来源，运行时生成指纹写入 Context Manifest。标签会移动，只记标签就无法知道当时用的是哪份内容，复现与归因都失效。外部 Skill 带来外部维护者、依赖和内容，自然语言说明也可能引导高权限操作；要经过来源核实、完整性校验、静态检查、隔离验证、人工评审、内部发布，运行时还要按任务重新授予不超过声明范围的权限。

2. 稳态与动态 Agent？相关性为何不等于资格？

稳态 Agent 用 AgentSpec 声明依赖，在构建 / 部署 / 启动期解析为精确版本和 Lock Manifest，重点是确定性；动态 Agent 用 ARD 从结构化的能力需求出发，混合检索候选，按需再用 RAD 解析远程 Agent 的协议与端点。相关性只决定排序；资源是否在线、调用方是否有权、环境是否兼容、风险成本是否允许由治理规则判断，过滤在分页前完成，撤回或越权的资源再相关也不能出现。

3. 仿真边界？Run 的四种状态？300 次零违规？

边界是授权和后果：不触达未授权的生产账户、数据与网络，不产生不可控的真实副作用，而不是“有没有请求真的发出去”。四种状态：执行状态、仿真有效性、证据完整性、任务质量，相互独立。300 次独立运行零违规，违规率的单侧 95% 置信上界约 1%（1 − 0.05^(1/300) ≈ 3/300），不是零，且依赖固定样本量、独立同分布、无选择性排除。
