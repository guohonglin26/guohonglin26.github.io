算法没变，执行方式变了

前面十二篇的算法，在小模型上一个脚本就能把生成、打分、更新串起来。换成 7B、70B 的生产模型，问题立刻变成另一类：几个模型装不进一组 GPU，生成一条回答要几秒而更新只要几百毫秒，新权重还得及时同步回生成端；两套引擎算出的概率对不上；一批任务里最慢的那条拖住所有人；奖励涨了却不知道该先查哪里。原教程第 18 章专门讲这些“让算法在集群上跑起来”的问题。这一篇是后来对照原文补上的，放在系列最后。

从脚本到集群：五个角色，三个瓶颈

原文 single-machine-to-industrial.md（18.1 节）

不管 PPO 还是 GRPO，一轮训练都是五个角色接力：Actor 生成回答，奖励模型或规则验证器打分，Reference 提供 KL 参照，PPO 还要 Critic 估优势（GRPO 用组内相对分数代替），最后训练进程更新 Actor 并把新权重交给下一轮生成。模型只有几亿参数时，五个角色可以在一台机器上依次跑完。规模一大，瓶颈出在执行方式上：几个模型装不进有限的显存；生成比一次参数更新慢得多；更新后的权重还要及时同步回生成进程。任何一环等太久，其他 GPU 就在空转。原教程的一句话：训练框架没有改变算法的数学定义，只是安排这些角色在什么设备上运行、何时交换数据、何时同步参数。

原教程给的选型顺序就是问题出现的顺序：第一次跑后训练，用 LlamaFactory 或 TRL，先确认数据、奖励和算法配置是对的；模型放不下、生成太慢，再上 veRL、slime、OpenRLHF 或 NeMo-Aligner，它们的区别主要在资源调度和训练、推理后端（如 slime 用 Megatron + SGLang，OpenRLHF 用 Ray + DeepSpeed + vLLM）；任务开始调用工具、轨迹长短不一，再看 AReaL、LlamaRL、AgentRL、ROLL，它们还要管理环境的创建、复位和回收。

长短不一会带来什么？假设一批里九道短数学题很快结束，一道工具任务要跑几分钟。同步训练等整批完成再更新，数据最新，但所有进程都在等最慢的那条；异步训练让完成的轨迹先进队列，训练进程持续取数据，等待少了，代价是有的轨迹由几轮之前的旧 Actor 生成，变“陈旧”了。AReaL 为每条轨迹记下生成它的策略版本，用重要性比率衡量陈旧程度，偏离 1 越远就降低权重，差太多直接丢弃。

ρtstale = πθ(at|st) / πθgen(at|st)
  • πθ(at|st)当前正在训练的模型选这个动作的概率训练端算出
  • πθgen(at|st)当初生成这条轨迹的旧模型选这个动作的概率生成时记录下来，要和轨迹一起保存

两者都是 0.2，比率为 1，经验仍然“新鲜”；0.1 对 0.2，比率 0.5，当前模型已经不太会这样做了。

训推不一致：同一组权重，不同的概率

原文 distributed-sync.md（18.4 节）、modern-industrial-practice.md（18.3 节）

参数同步解决的是版本问题：生成端和训练端拿到同一组权重。但同一组权重，不等于同一组概率。生成端用 vLLM 或 SGLang，配 KV Cache 和 FP8 / BF16 低精度，一切为速度服务；训练端用 FSDP 或 Megatron，BF16 / FP32，还要保留反向传播的计算图。同一个 token，生成端算出 0.30，训练端重算得 0.29，两边都“没错”。MoE 模型更麻烦：两套路由实现略有差异，同一个 token 可能激活不同的专家。这就是训推不一致（Training-Inference Mismatch）。

它为什么要紧？PPO 的比率 rt = πθ / πold 有个前提：分母必须是生成动作时真正使用的策略。如果回答来自生成引擎，训练端却用另一条计算路径重算 πold，那 rt 在更新开始之前就已经不准了。裁剪只能限制参数更新的幅度，修正不了两个引擎算出的概率差。原教程举的数字：生成端记录某 token 的对数概率是 −1.32，训练端（版本也晚了一步）重算是 −1.51，比率 e−0.19 ≈ 0.83，没有任何采样随机性，却偏离了 1 约 17%，而且会安静地混进每一次更新。

排查顺序：先核对生成端用的模型版本，确认同步完成；再用同一批 token 分别记下两端的对数概率，看误差集中在哪；然后对齐精度和算子；MoE 再额外记录专家路由。修正手段包括：直接保存生成时的对数概率（不拿重算值冒充行为策略），训练前重算并逐 token 对比，用截断重要性采样（TIS）限制极端比率，以及 MoE 的路由回放（R3）。

资源安排上，原教程用 veRL（HybridFlow）说明一种常见拆法：ResourcePool 把 GPU 分组，模型可以共享一组 GPU（colocate），也可以各占一组（disaggregated）；Worker 封装一个模型实例，Actor Worker 管损失、反向和优化器，Rollout Worker 管批量生成和权重同步；Driver 是单控制器，按顺序执行算法主循环：同步权重 → 采样 → 打分 → 估值 → 更新 Actor → 更新 Critic。

两端对数概率差多少，比率偏多少

比率 = e差值。PPO 裁剪常用 ε = 0.2，对应的对数差区间是 [ln 0.8, ln 1.2] ≈ [−0.22, +0.18]：超出这个范围，这个 token 一进入训练就已经顶到裁剪边界。

易混辨析：经验陈旧 vs 训推不一致

经验陈旧：轨迹由几轮之前的旧版本 Actor 生成，是版本差。异步训练必然出现，用版本号记录、重要性比率降权或丢弃来处理。

训推不一致：版本相同，但两套引擎的精度、算子、MoE 路由不同，算出的概率不一样，是计算路径差。用记录真实行为概率、对齐精度、TIS 和路由回放来处理。两者会叠加，都会让 PPO 的比率在更新前就失真。

奖励与选题：两类奖励，只练“有时对、有时错”的题

原文 single-machine-to-industrial.md 第 2 节

后训练常用两类奖励。可验证奖励（VR）来自确定性的验证函数，比如抽出最终答案和标准答案比对、运行单元测试，标注成本接近零，噪声来自解析器、测试覆盖和执行环境，要防的是测试覆盖不足和规则被绕过。偏好奖励（PPR）来自从成对偏好里学出来的奖励模型，适合开放对话、写作、安全和风格，噪声来自标注分歧和奖励模型的泛化误差，要防模型去钻奖励模型的偏差。产品模型通常两类都要，可以按任务类型加权组合；生成式奖励模型（让大模型输出“A 更好”或“B 更好”，可以带推理过程）是近两年的趋势。代码任务还可以分三层验证：规则层过滤格式和明显硬编码，公开测试验证已知行为，隐藏测试和模型裁判检查泛化。

不是所有可验证的题都值得练。原教程引用字节 Seed-Thinking 的做法：先用基座模型对每道题采 16 次，统计通过率，只保留通过率在 0.1 到 0.9 之间的题，再按难度分桶。道理和第 9 篇的 GRPO 一样：一组回答全对或全错，组内方差为零，优势为零，这道题对梯度没有贡献。DAPO 的动态采样也是持续监控组内方差，降低低方差题的采样比例。

混合多种奖励时最大的工程问题是尺度不一致：数学题是 0 / 1，代码通过率在 0 到 1 之间，生成式奖励可能在 −3 到 3，长度惩罚在 ±0.5。直接相加，大尺度的那项就主导了梯度。标准做法是按任务域在 batch 内做 z-score 归一化，再相加。

算一笔账：GPU 小时

原文 single-machine-to-industrial.md 第 3 节

估算成本不是为了精确到小时，而是快速判断一个方案在手头资源下可不可行。原教程给的公式：训练总 FLOPs 约为 6 × 激活参数量 × 训练 token 数（前向 2 倍、反向 4 倍），除以单卡峰值算力和实际利用率（MFU，典型 30%–50%），再换算成小时。MoE 模型只算每个 token 实际路由到的专家参数。

GPU-hours ≈ 6 · Nactive · Ntokens / ( GPU_FLOPS · MFU · 3600 )
  • Nactive每个 token 实际参与计算的参数量Dense 等于总参数量；MoE 只算激活的专家
  • Ntokens训练 token 总数RL 里还要算上生成的 token
  • GPU_FLOPS单卡峰值算力查规格，注意精度
  • MFU实际达到的算力比例典型 30%–50%

RL 比 SFT 难算，因为一步包含四部分：生成回答、更新 Actor、Reference 前向、计算奖励。原教程给的典型配比（7B 模型、每步 512 个提示 × 8 条回答）里，生成占总计算量的 50%–60%，这也是各家框架都要单独优化生成吞吐、异步调度和参数同步的原因。控制成本的几条：数据筛选优先于堆算力；先在小模型上验证算法和超参再放大；BF16 比 FP32 快约 2 倍，FP8 再快 1.5–2 倍但更考验稳定性；各阶段保留检查点，避免从零重训。

四层排查：按因果顺序，从上往下修

原文 modern-industrial-practice.md（18.3 节）

奖励、KL 和熵、loss 与梯度、两端概率，四条曲线摆在一起先看哪条？原教程的答案在因果顺序里：数据和奖励决定模型学什么，策略指标描述模型怎样改变，数值指标反映参数能不能正常更新，训练系统决定日志里的概率是不是真的来自生成回答的那个策略。上游错了，下游曲线一定跟着乱；反过来，下游的工具修不了上游的问题，梯度裁剪只能限制步子，奖励衡量错了目标，裁剪之后每一步仍然朝着错的方向走。这和第 12 篇“由外到内”的排障顺序是同一个思路。

原教程第一层的例子：200 步里训练奖励从 0.30 涨到 0.80，MATH-500 一直是 42%，平均回答长度从 400 涨到 1200 token。奖励翻倍而独立评测不动，说明模型学到的是更容易得奖励的形式。第二层看KL 和熵要一起读：参考策略 [0.5, 0.5]，当前 [0.80, 0.20] 时 KL ≈ 0.19、熵 ≈ 0.50；集中到 [0.95, 0.05] 时 KL ≈ 0.49、熵 ≈ 0.20。KL 单独变大可能只是正常脱离 SFT，熵单独下降可能是找到了好解法；两者同时陡变，才说明模型在远离参考的同时放弃了修正的余地。但也要排除题太简单：全组全对时熵也会自然下降。第三层看 loss 尖刺和梯度暴涨，NaN 之前通常有前兆；固定一个 batch 反复跑，稳定复现说明问题在这批数据或某条确定的计算路径，随机出现则更可能是精度或优化器状态。第四层就是上一节的训推不一致。

数据工程：一条轨迹的一生

原文 data-engineering.md（18.5 节）、industrial-post-training.md（18.2 节）

多机训练每小时能产生几十万条轨迹，从任务生成、环境执行、评分、存储到回流，任何一环没处理好，要么数据大量流失，要么错误轨迹反复进入训练。任务从哪来：公开基准适合冷启动和回归，合成任务扩充特定类型，交互环境任务覆盖终端、浏览器和工具，真实失败样本带来题库覆盖不到的新组合，安全与对抗数据守住边界。原教程举的公开数字：MiniCPM 5 约 3 万个高质量种子提示，三分之二是推理、数学、代码，三分之一是工具与代理任务；Qwen-AgentWorld 从 20 个领域 5000 个种子任务起步，两周扩到 3 万个。调度上优先采样近期正确率在 0.3 到 0.7 之间的任务，失败案例加权，已经大量成功的类型降频，并持续混入少量安全任务，防止能力提升时边界被遗忘。

记什么：很多实现只存提示、回答、奖励和对数概率，够算一次梯度，却不够排查“奖励为什么突然下降”。原教程建议分五层保存：任务层（类型、难度、来源、环境配置、模板版本）、轨迹层（每步 token 和对数概率、采样参数、模型版本）、交互层（工具调用和返回、执行输出、错误）、奖励层（每个奖励函数的值、权重、聚合方式、测试通过数）、系统层（worker、时间戳、检查点、镜像版本、随机种子）。超时、环境错误、格式错误的轨迹单独标记，既不直接混进训练，也不直接删掉。进训练前还要过质量关：高分可能来自验证器漏洞或格式绕过，低分也可能是奖励函数报错或工具超时。合格的轨迹再回流到下一轮 SFT、奖励模型训练和任务池，形成后训练闭环。

1. 放大到集群多出了哪些问题？什么时候用异步，代价是什么？

算法没变，执行方式变了：几个模型装不进一组 GPU；生成远慢于更新，训练 GPU 空等；新权重要同步回生成端；Agent 任务还要管理环境。轨迹耗时差别大（工具调用、浏览器、长交互）时用异步，减少等待；代价是经验陈旧，要记录生成版本、用重要性比率降权，差太多就丢弃。数学、代码这类耗时接近的任务先用同步。

2. 同一份权重为什么概率对不上？为什么裁剪修不了？

生成端（vLLM / SGLang、FP8 / BF16、推理算子）和训练端（FSDP / Megatron、BF16 / FP32、训练算子）计算路径不同，MoE 路由也可能不同。PPO 比率的分母必须是真实的行为策略，分母一旦用重算值，比率在更新前就已失真；裁剪只限制更新幅度，不纠正概率本身的偏差。要记录生成时的对数概率、逐 token 对比、对齐精度，用 TIS、路由回放等方法修正。

3. 为什么排查要从数据与奖励开始？

四层是因果顺序：奖励决定学什么，策略指标描述怎么变，数值指标反映能否正常更新，系统决定日志里的概率是否可信。上游出错，下游一定跟着乱；下游的工具（裁剪、优化器、降学习率）修不了上游，只会让模型更平稳地朝错误目标走，把故障藏得更深。
